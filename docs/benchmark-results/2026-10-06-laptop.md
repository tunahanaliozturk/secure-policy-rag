# Pipeline latency, 2026-10-06, laptop

## What was measured

Everything on the request path except the model call: redact the question, embed it, retrieve under row-level
security (full text and vector, fused), build the prompt, verify the answer, redact it, and insert the audit record.
The model is `ScriptedModel("faithful")`, which answers in microseconds, so these numbers are the overhead the design
adds on top of a real model call. The model call itself was not measured: there is no API key on this machine.

Harness: `benchmarks/pipeline_latency.py --rounds 5`. The 69 questions of `eval/retrieval.jsonl`, each asked as its own
demo user, five rounds, after five warm-up requests. Sequential, one request at a time, so this is per-request cost,
not throughput. No HTTP layer.

## Setup

- Intel Core Ultra 7 255H (16 logical processors), 32 GB RAM, Windows 11 Enterprise.
- Python 3.14.6, asyncpg 0.31.0, fastembed 0.8.1 with onnxruntime 1.30.0, BAAI/bge-small-en-v1.5.
- Postgres 18 with pgvector 0.8.7 in Docker Desktop, reached over the published port on 127.0.0.1.
- 35 documents, 149 chunks.

## Results

| Configuration | p50 | p95 | p99 | mean |
|---|---|---|---|---|
| onnxruntime default threads (one per core) | 89.7 ms | 161.5 ms | 266.5 ms | 92.6 ms |
| onnxruntime capped at 2 threads (shipped) | 17.3 ms | 21.0 ms | 36.1 ms | 17.8 ms |

345 requests per row.

## What the first row taught us

The first run was five times slower than its parts added up to. Measured alone, embedding a question took 5.3 ms and
retrieval 4.5 ms. Inside the pipeline, retrieval took 84 ms. The difference: onnxruntime's default thread pool, one
worker per core, keeps spinning after each inference while it waits for more work. On a 16-thread laptop that starved
the event loop and Docker Desktop's port forwarding for the tens of milliseconds that followed, which is exactly when
the retrieval queries ran.

Capping the embedder at two threads fixed it (`embedding.FastEmbedder`). Per call, with a retrieval after each
embedding, medians over 40 calls:

| onnxruntime threads | embed | retrieve right after |
|---|---|---|
| default (16) | 6.6 ms | 83.7 ms |
| 1 | 8.8 ms | 5.5 ms |
| 2 | 7.2 ms | 5.6 ms |

The embedding got 0.6 ms slower and the request got 72 ms faster at the median. Batch embedding at ingestion is the one
place more threads would help; at 149 chunks it does not matter.

## Caveats

- One machine, one run per configuration, a laptop with background processes. Treat differences under a few
  milliseconds as noise.
- Docker Desktop on Windows adds a network hop that a Linux host would not.
- No concurrency. Under concurrent load the embedder, which runs in a worker thread, is the first thing to queue.
